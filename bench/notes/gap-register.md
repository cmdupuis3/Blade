# Compiler gap register — what expert Fortran does by hand that Blade could derive, and does not

Architect's bridge from this suite to the next phase. One entry per gap; factual; evidence is
a `blade emit`/`blade plan` excerpt, a diagnostic code, or a `src/` location found cheaply.
"Direction" is one line, not a plan. Lane column: whether the C++ and LLVM lanes differ.
Evidence dated 2026-10-17, compiler 0.20.0, this worktree's `bin/Release/net10.0/Blade.exe`;
blade-B's items cite `notes/llvm-acceptance-B.md`.

## Notes

- G1 is the one gap that turns a hypothesised loss into a win on the suite's headline kernel
  (its mechanism was corrected by blade-A: a single-accumulator dot, not a jam); G15 is the
  C++-lane-only trap that decided the `prodsum` spelling; G16 is a correctness finding, not a
  performance gap, and lives here only so the next phase does not lose it;
  G2/G3 are the same missing primitive seen from two sides; G4 removed a kernel from the
  suite; G7/G11 are mt8 holes; G8 contradicts the idiom ladder's top rung; G12/G13 are
  contract-shaping constraints the Blade sources carry.
- Items marked "blade-B" are taken from `notes/llvm-acceptance-B.md`; the architect did not
  re-run them. Items with a probe file name were emitted by the architect at extents 11–1009
  (no timing).
