1. **BLOCKER — T3 does not prove first-failure equivalence.** Brief §2/T3 checks writes/repeatability but does not require every value producer and seed to be total, already evaluated, and available at gk. `assignedAnywhere=false` is none of those proofs. Existing code validates the key column before gathering values, gathers by group/perm order, then executes each peel in declaration/group order (`CodeGenBinding.fs:735, 791, 2811-2816`). The proposed source-order pass moves value evaluation and seeds ahead of those phases.

   Counterexample schemas: adapt sql-group-by/051's invalid final positional key; use a deferred value producer whose first cell performs a missing compound-key read. Originally gk's invalid-key BL8006 wins; forcing/reading that producer at the first row can report the missing key first, at another span. Alternatively give a later peel a pure but failing scalar seed (a keyed read or an empty unseeded reduction). W+F alone does not prove that seed total: hoisting it can beat the earlier peel's empty-group BL8003 or an intervening BL8013. A value/seed bound between gk and its peel also cannot simply be referenced at gk.

   **Fix:** v1 accepts only already-stored, dominating, shape-compatible sources and total, dominating seeds; prove all moved reads in bounds and preserve negative-row nonreads. Otherwise retain the original phases. Do not force a deferred value producer early. Keep BL8006 key validation order/span, and leave each BL8003 check at its original peel and first empty group. Preserve prior group stores before a later group fails; private speculative accumulators are not permission to publish later named outputs early. Cross each of: /051, missing-key producer, /056 refusal, two differently failing peels, empty seeded/unseeded groups, an intervening display and BL8013. Compare exit, diagnostic location, emitted stores, and observable output prefix. Stored total inputs with total seeds eliminate this failure-order objection; stable member order alone does not.

2. **BLOCKER — T3's initialization recipe is not an exact fold.** Steps 3–4 say initialize an unseeded state from the first element, then call `k(acc, v[i])` on that same row: this doubles the first element unless the first-row update is skipped. Initializing only on first encounter also leaves statically declared empty groups without their seeded result. A generic pure two-argument callable has no inferred identity. Seeds may depend on row information, not merely be uniform constants.

   **Fix:** separate seeded, unseeded, prodsum, and count state machines. Unseeded: copy the first value and consume it exactly once; seeded: execute the original chain from that exact seed, including empty groups; prodsum: preserve its actual initialization and rounding. Restrict seeds to a supported row-independent form or model their dependencies explicitly. Pin singleton, empty, nonzero seed, signed zero, and noncommutative `3*a+b` cases. No universal -0 identity substitution.

3. **HIGH — T3's licensed change is legal association, a value change, and potentially a speed regression; it has no 1e-9 guarantee.** A source-licensed addition may use an ordered chain; the licence permits, rather than requires, eight lanes. But one group with values `[1e16,-1e16,1,0,0,0,0,0,1]` gives 2 in the ascending chain and 1 in the illustrated eight-lane scheme (the last 1 disappears in lane 0). This is far beyond the stated pin tolerance. Integer addition/multiplication and an arbitrary integer callable are not interchangeable claims: `3*a+b` must keep its original, unlicensed order.

   **Fix:** delete “within the harness's 1e-9 rule” as a universal claim. Keep default EXPECT fixtures association-insensitive, test licensed numerical error separately, and report changed bits. `tests/OptDiff.fs:134-155, 203` pins REPRO=1/CONTRACT=off and compares normalized output plus exit status for changed C++: it tests strict gate equivalence, not this licensed change, hidden named stores, or the LLVM implementation. Add explicit licensed cancellation/accuracy and performance comparisons. Do not loosen pins to bless a miscompile. Few-group lane scheduling is a later performance choice.

4. **BLOCKER — T3 misstates EnumIdx order and negative-key handling.** Dynamic discovery is first occurrence in all three implementations: C++ `CodeGenBinding.fs:676-719`, LLVM `EmitLlvm.fs:3793-3797, 3848ff`, interpreter `Interp/ArrayOps.fs:1968-1977`. Positional order is 0..G-1, including empty groups. EnumIdx order is the DECLARED enumeration order, not sorted numeric key order (`CodeGenBinding.fs:754-802`; LLVM :3815-3835; interpreter :1958-1966). Declared negative enum members are valid, not dropped (`docs/features/sql.md:345-351`).

   **Fix:** retain three separate regimes. Test dynamic keys [7,3,7,9,3] -> counts [2,2,1], and a deliberately unsorted enum with a negative member, e.g. [7,-2,3]. Hash-table iteration order must never define output order. Extents(gk) remains the stored array of group sizes, not a scalar group count.

5. **MEDIUM — T2's specified order is correct; “CSR” alone does not guarantee it.** The runtime enumerates valid tuples row-major/lex (`src/cpp/index_types.h:229-232, 265-270`). Probe i ascending and retain ALL right row indices j ascending inside every bucket: this yields exactly the same sequence, even with duplicates on both sides. Sorting bucket keys is harmless if bucket traversal never determines left output order.

   Smallest duplicate stress case: left keys [1,1], amounts [1,10]; right keys [1,1], amounts [2,3]. Compound and correct CSR give coordinates [(0,0),(0,1),(1,0),(1,1)] and values [2,3,20,30]. Deduplicating gives too few rows; prepend-built buckets give [3,2,30,20]; a right-major probe gives [2,20,3,30]. The seeded `3*a+b` fingerprints are respectively 171, 209, 273. There is NO counterexample to the explicitly stable left-major/right-minor algorithm; these are counterexamples to plausible weaker implementations.

   **Fix:** specify forward stable bucket fill and pin this 2x2 case, interleaved different keys, all-equal skew, negative keys, no matches, and tails. Never apply grouping's negative-key drop to equality. Positional left values outside the build domain have no match; do not introduce BL8006.

6. **HIGH — T2's skipped-work and 64 MB argument need replacement.** It removes the all-pairs equality enumeration (replacing it with build/probe equality), identity mask pass, packed-mask copy/enumeration, coordinate reverse hash, nonmatch payload evaluations, dense payload pool and full-pair scatter. It retains stored inputs, every match payload, the named compact output, and the existing consumer folds. Thus “only == and pk on nonmatches” omits substantial representation work; the purity proof applies to skipped evaluations, while a separate demand proof licenses dropping representations.

   With N=100,003 and M=20,011, P=2,001,160,033; expected J=P/10,007≈199,976 for balanced keys. 19.4P=38.82 GB is TRAFFIC, not peak storage. The brief's own six rows sum to 20.375 B/pair=40.77 GB. Moreover B-work/p2b.cpp.txt:270 unconditionally writes the compact buffer for EVERY pair, adding 8 B/pair of logical stores: at least 28.375P=56.78 GB under that counting convention. Repeated writes may hit one cache line; these are not measured DRAM bytes. The by-value vector<bool> constructor call adds copying work too.

   The cap still fails independently: the product pool alone is 16.009 GB; two bool pools add 4.002 GB; two live bitvectors add ≈0.500 GB, before tuple/hash storage, pointers and inputs. At the pilot N=2003,M=1009, P=2,021,027: the same estimates are 41.18 MB table traffic / 57.35 MB including branchless stores, versus ≈20.72 MB for those live pools. “39 MB” is neither a complete traffic count nor a peak estimate.

   **Fix:** publish separate operations, logical traffic, allocated/live bytes and measured peak working set. Include output sizing/growth or a counting pass: J is not known beforehand. A general all-equal join still has J=NM and cannot satisfy 64 MB while storing J; bound the generated distribution or decline oversized results. Include runtime baseline and all named outputs in the eventual cap measurement.

Boolean equality alone is not a failure-order proof. Keep the interpreter independent of the shared C core.
