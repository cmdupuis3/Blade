## Recommendation: one ordinary array return, using its already-owned local root

Implement only the existing return-donor plan for an ordinary capture-free outlined function returning a static plain dense rank-one Float64 array. First positive is A02/030. Reuse one known-owned dead local backing as the final map destination, preserve its single tracking record, and return that same pointer through the existing array ABI. No general let-to-let chain consumer, tuple-call cleanup, alias-copy retention fix, dynamic/capacity reshape, in-place input update or early free in this checkpoint.

This is a useful bounded storage change with no prerequisite tuple-lifetime repair: 030 already has a proper outlined function pool scope and correct temporary/result cleanup. Existing planning supplies the liveness/unaliasing license; renderer checks establish that its proposed root corresponds to an actual owned backing that this fill can safely use. General chain/tuple cases remain explicit unconsumed plans after this first consumer; the card must not claim all PM01 routes complete.

## Proposed admission and identity chain

The small first implementation admits only all of the following; any missing proof takes the original fresh-result path and records a backend decline for the proposed return reuse.

1. Actual renderer entry is ordinary emitFunctionBody for this numeric callable ID, capture-free and nonrecursive, with array return. No tuple/capturing/kernel inline, CUDA/MPI/OMP strategy, lifetime events anywhere in its body, or unresolved/indirect renderer route. For this first card exclude functions with any let-donor entries; only the single return-donor contract is consumed.
2. Tail is exactly IRCompute(IRApplyCombinator info), optionally repeated compute wrappers, reached through the ordinary outer IRLet continuation spine. No branch, match, call-result, compose, row-return, bare virtual range or hidden nested return form. Donor definition is a direct prior body let of the same computed map shape, not a parameter/alias/view or an inner value whose scope ended.
3. Return output, donor type and source input are exactly matching static plain nonsymmetric rank-one Float64 groups with positive literal extent. No wider-capacity compatibility, reinterpretation, dynamic/compact/ragged/packed/strided shape or unit/layout conversion. The first return map has one named rank-one operand, scalar peel, no Reynolds/special schedule and a scalar Float64 kernel. Permit only direct scalar arithmetic over its scalar parameter, scalar literals and already-bound local scalar snapshots; no calls, array-valued captures, keyed/hidden array reads, assignment, nested loop/array construction or source effects. Keep the original AST arithmetic/flags, rather than constructing a replacement expression.
4. `tryReturnDonor cl.Id` yields donorID; c.ArrSlots[donorID] is already APool d with exact groups/element. It must be the direct, uniquely matching `(d, trackingSlot)` entry in the currently active ordinary function PoolScope, whose InlineId=None and KnownIds does not include donorID. No enclosing/caller scope, borrowed pointer, GEP base, released region or anonymous pointer comparison is accepted. In the bounded ordinary function there is exactly that function scope active at this point. The plan's donor ID is a body-local fresh computed allocation, not merely any current value with equal extent.
5. The return operand is already APool inputBacking. Establish its allocation origin: a different exact allocation entry in this same scope, or an actual formal-array parameter value that predates the function's fresh donor allocation. The input backing must be distinct from d and its root must not alias d; merely different SSA names do not prove that. Unknown-loaded pointers, views and non-root GEPs decline. A named AVirt/AVirtFlat operand declines WITHOUT forcing it as part of a speculative reuse attempt.

The upstream plan supplies whole-body liveness and no retained-handle proof. These renderer gates are conservative realization checks, not a new general alias analysis. They deliberately exclude the main source of latent unsoundness: an AVirt input may close over old p, while its producing let has not consumed p yet. Constructing a producer or seeing an equal-sized ArrVal is not proof that old p's cells were read. Requiring the input's completed APool and a kernel with only bound scalar snapshots closes that delayed-read path. A scalar mean computed from p holds its value in a scalar slot; it carries no backing reference and remains usable after p is repurposed.

For030, q was fully filled while reading p before the final map begins. The final producer reads only q's independent backing; p has no remaining old-value consumer. Its destination stores can therefore overwrite p without aliasing the source or changing failure/traversal order. Caller-owned input never becomes a donation target.

## Minimal implementation shape, after approval only

Within emitFunctionBody's array-result arm, replace its one `materialize c (emitArr c cl.Body)` expression with a local return-aware walk. For each outer IRLet call the exact existing bindLetIn once, in original order, then continue. At the final tail run the preflight above using the existing table, slots and scope. Without a complete match, evaluate/materialize that tail once through the old path. Do not rewind emitted text or try a rendering and then reevaluate on fallback.

For an admitted tail invoke the unmodified, combined applyToArr once to obtain its ordinary dense AVirt. Extract the existing dense fill body from materialize into a shared private helper accepting a destination pointer and ArrVal, and use that SAME emitNest/readCell/coerce/storeCell code for both fresh allocation and donor fill. First implementation need only admit the ordinary AVirt branch, not AVirtFlat or other special producers. It must not introduce a destination override global/context field or alter allocPool's behavior. If an actual emitted shape contradicts a preflight guarantee, refuse this LLVM emission explicitly before any destination store; do not emit an Applied outcome or render/evaluate a second copy.

Return `{ producer with Src=APool d }`. Do not call allocPool, add a second tracking slot, copy the donor into a new binding or null/suppress any unrelated scope record. Original donorID and its local slot still denote the same backing; its previous value is dead and no further old-value read is permitted. At the ordinary return, existing `popPoolScope c (Some d) true` excludes that one record, frees q exactly once and emits `ret ptr d`. Shape checks and array ABI are unchanged. Retaining the one existing ownership record avoids duplicate frees and avoids extending a released or caller-owned root.

Required backend diagnostic is distinct from the shared planner Applied decision: e.g. `pool-reuse-llvm` Applied only after destination fill is selected, with numeric function/donor IDs and allocation-origin evidence; Declined with an exact capability/ownership blocker otherwise. The shared plan may remain Applied while this bounded backend declines. General let/tuple cases remain reported as outside the consumer, not mislabelled backend successes. Keep BLADE_POOL_REUSE gating in the existing planner/table; no cached environment variable or extra default policy.

Expected030 raw change: function allocates only p+q, final GEP/store targets the original p allocation, no separate returned allocation/slot, q's own slot loads/frees once, p is not freed and ret names p. Off retains three allocations/two temporary frees. Pointer register numbers can change; proof must map IDs to actual allocation roots instead of pinning the historical numbers. Each invocation allocates its own p; two live returned arrays from two calls must remain distinct. Module-level input/output lifetime is unchanged.
